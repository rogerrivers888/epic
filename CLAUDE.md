# Epic — working agreements for agents

Read `docs/requirements.md` (governing) and `docs/technical-constraints.md` before changing behaviour. `docs/ux-research.md` explains why screens look the way they do.

## Constraints that come from the owner, not the docs

- **Prior instructions must be quoted, not asserted.** If you believe the owner set a constraint earlier, quote the exact message before acting on it. If you cannot find it, say so and ask; do not work around a rule you cannot cite.
- **Secrets come from Doppler at runtime.** Never in the repo, never in `.env.example`, never set directly as platform (Railway) variables. Local development reads a git-ignored `.env`; everything deployed is injected by the Doppler → Railway integration, which the owner configures by hand.
- **Anything that holds a secret, spends money, or sets a billing cap is the owner's to do.** Creating or renaming services, domains and non-secret configuration is fine for an agent when asked; adding provider keys, enabling paid sources, and provider-side spend caps are not.
- **Everything is reviewed by Codex before it is called done** (owner, 4 Sep 2026: "Keep on going. Don't stop till you're completely done. And make sure everything is reviewed by Codex."). `codex exec review --base <branch>` (or `--commit`, `--uncommitted`) — run it against the range about to be handed over, report what it found, and say what was done about each finding, including the ones not acted on and why. It does not replace the tests or checking the deployed site; it is the pass that catches what neither of those would.
- **A migration and the tests that depend on it are committed together, never separately** (owner, 21 Sep 2026). The test database is built from `git ls-files migrations/`, so an uncommitted migration is invisible to every other session — a committed test that needs it fails for everybody until it lands, and the failure names neither the cause nor the owner. `test/helpers/db.js` prints one line naming any untracked migration it skipped; if failures make no sense, read that line first. This bit twice in a day: once when a broken uncommitted migration took 22 test files down across every session, and once when a correct one was committed after the tests that needed it.
- **Never edit a migration that has already run; write a follow-on** (owner, 25 Sep 2026). `schema_migrations` keys on the filename, so an edited file is skipped wherever the original has been applied — the test database, a peer's local database, production — and the committed copy and the edited copy quietly drift. Migration 248 was found modified in the shared tree after it was committed, with four sessions blocked behind it. The fix for a migration that has run is the next number, never the same file.
- **Every diagnostic has a can't-speak state** (owner, 21 Sep 2026). A signal without enough evidence behind it says so, rather than recommending an action. This has now produced the same fault three times in one day, each time as a confident instruction to retire something real: "nobody has ever opened this", true of every mapping against a corpus of twenty-nine opens; refusals counted as times a question was asked; and "most words die unconfirmed", printed beside a harvest that had worked, because the count it read meant *newly inserted* and not *written down*. So: a verdict names the evidence it is drawn from and withholds itself when that evidence is too thin — `null` and a reason, never a number that happens to be nought. **Saturation dominated by singletons is not a rate**: a hundred words each seen on one place is not a subcategory still teaching us a hundred words, and a threshold set on sixty places in one county is a provisional number until a clean run says otherwise. **The same shape inside a retry loop runs away** (26 Sep 2026): the classifier drain read a 429/401 error body as a result — no `looked` key became −1, −1 is not 0, so it spun 108 times in one second. A loop's stop condition comes only from a parsed, well-formed answer; anything else is "can't speak" and means wait, not continue. **A capped list is not a complete one** (E1, 26 Sep 2026): asked whether a trip to Crystal Palace existed, a query returned six rows newest-first, none of them Crystal Palace, and that was reported as "no such trip exists" — the trip from the original complaint was there, created on 6 September, below the cap. It cost six days on a check that took a minute once the premise was fixed. A result with a `limit` on it can say what it found; it cannot say what is absent. Absence is claimed only from a query without a cap — a `count(*)`, or a filter narrow enough that the limit was never reached — and otherwise the answer is "not in the first N".
- **A census text query is always fenced by a type where any type applies, and bare only where none does — and then marked text-sourced** (owner, 21 Sep 2026). A bare text query on the IDs Only mask cannot be checked against anything, because `types` is a Pro field the census may not buy: "climbing" would count everything *named* Climbing. With `includedType` set the worst case is a wrong member of a real category rather than an invented one. `censusQuestions.js` holds both forms and `SOURCED` says which a slice used; a text-sourced count carries that label on the board so it can be judged before it is trusted.
- **Done means: main is green after the final commit — re-run, not remembered — then Codex, then checked on the deployed site** (owner, 21 Sep 2026). Codex reviews the diff; it does not prove main. On 21 Sep a Codex pass came back clean on every file in a batch while a test that batch had broken was already failing on main, because the suite had been run before the last commit rather than after it. The order is not interchangeable: a green suite from ten minutes ago is not evidence, and a clean review is not a green suite.
- **That sequence is `/ship`, and it pushes itself when it is clean** (owner, 21 Sep 2026). `.claude/skills/ship/SKILL.md` runs the hand-over in order — range, suite, `codex exec review`, act on every finding, suite again, push, deployed site — and **pushes without asking when the suite is green and Codex raised nothing actionable**. This narrows "approve first, Codex after": his approval gates what gets *built*, not a clean batch shipping. It still stops and reports rather than pushing when the suite is not green after the final commit, when a finding is being left unfixed, when the batch touches a migration, a secret, a provider key or a spend cap, or when the review failed to run — a review that did not happen is never reported as clean. Unattended is not silent: every finding and its disposition is still reported.
- **Codex runs on the Epic account, not Parcelhero** (owner, 21 Sep 2026). There are two ChatGPT Business accounts on this machine and only Epic's may bill for Epic's reviews. The switch is `CODEX_HOME`: `.claude/settings.local.json` points this repo at `~/.codex-epic` (roger@epic.day), while the default `~/.codex` stays on Parcelhero. That settings file is gitignored, so **a fresh clone does not have it** — until it is restored, prefix codex commands with `CODEX_HOME=$HOME/.codex-epic`. Never `codex logout` to change account: two homes hold two logins side by side.
- **Never commit from the shared index: write in the shared tree, commit and push only from a worktree off `origin/main`** (owner, 26 Sep 2026; supersedes hunk-staging in the shared tree, 25 Sep). The index is shared, and any check followed by a separate commit races every other session: on 24 Sep `git commit -- <path>` swept a peer's lines twice in a day, once between a `git diff` and the commit after it, and on 26 Sep a `git diff --cached --stat` that showed three files of one session's own was followed — after a test run of a few seconds — by a commit that also carried the harvest session's staged migration 260, because `git commit` takes the whole index as it is at that instant (F8, the third time). Hunk-staging cannot close a race; a tree nobody else writes to can. So in the shared tree only edit files, and never `git add`, `git commit`, `git commit --amend`, `git mv`, `git stash`, `git checkout -- <file>` or push `main` — its local `main` routinely holds other sessions' unpushed commits, and pushing it ships their unfinished batches. Every commit, every time:
  ```
  git fetch origin
  git diff --binary origin/main -- <your files> > /tmp/<name>.patch
  #   the working tree against origin/main itself — not the shared index, not the shared HEAD.
  #   read it and cut out every hunk that is not yours, whether uncommitted or in somebody's unpushed commit.
  #   a new file of yours is not in it: copy it across.
  git worktree add --detach /tmp/epic-wt-<name> origin/main
  cd /tmp/epic-wt-<name> && git apply /tmp/<name>.patch
  cp <repo>/.env . && ln -s <repo>/node_modules node_modules && ln -s <repo>/apps/api/node_modules apps/api/node_modules   # + apps/web/node_modules for web work
  git add <your files> && git diff --cached           # nothing else is here to sweep in
  git commit -F - <<'MSG' … MSG
  (cd apps/api && npm test)                            # the full suite, after the last commit, before the review
  CODEX_HOME=$HOME/.codex-epic codex exec review --base origin/main
  #   read every finding, and fix it in the SHARED tree — then carry it across the same way:
  #   git diff --binary $(git -C /tmp/epic-wt-<name> rev-parse HEAD) -- <your files> > /tmp/<name>-fix.patch
  #   (run in the shared tree; cut to your hunks), git apply it here, commit, suite, review again.
  #   A file NEW in this batch is untracked in the shared tree, and that diff would delete it: copy it across instead.
  #   Or stop and report it. Codex exits 0 with findings — the exit code is not the gate, you are.
  git push origin HEAD:main                           # only with nothing actionable left; the pre-push hook runs the suite once more
  cd <repo> && git worktree remove --force /tmp/epic-wt-<name>
  ```
  **The patch is cut against `origin/main`, the base the worktree is made from — never against the shared tree's `HEAD` or index.** Local `main` often holds other sessions' unpushed commits and the index their staged hunks; a diff against either leaves out what is not in `origin/main`, and the patch then fails to apply or applies without what it depended on. A diff against `origin/main` shows everything that differs — yours, theirs, uncommitted or not — so every hunk that is not yours is visible and can be cut; and what you pushed earlier is already in `origin/main`, so it drops out by itself. `--binary` carries a changed image or other binary file, which a plain diff reduces to "Binary files differ". If a hunk of yours sits on top of somebody else's that is not in `origin/main`, do not carry theirs or cut around it: find its owner (`ListAgents`) and ask them to push first. If the patch does not apply, `origin/main` moved under your files: fetch, cut it again, and read what changed before re-applying — never force it. **The shared tree is the one copy of your work that outlives the worktree**, so nothing is ever edited only in the worktree: a fix made there alone is gone when the worktree is removed, and the next patch cut from the shared tree reverts it without a word. A follow-on fix is a new commit in a new worktree, never an amend. Whatever is yours stays edited in the shared tree too, so its working copy keeps your change; if someone else's hunk is in a file you are cutting a patch from, leave it out of the patch and leave it in the tree for its owner.
- **No GitHub Actions or hosted CI** (owner, 21 Sep 2026). Run the files you touched before committing (`npm run test:files -- test/<file>.test.js`), and the full suite under the lock before pushing (`npm test`, which takes it). A `pre-push` hook in `.githooks/` does the second and blocks the push if anything fails — `git config core.hooksPath .githooks` once per clone. **Never push with `--no-verify`**: the hook is the only thing between a broken commit and four other sessions pulling it.
- **A red suite in the shared tree is not evidence either way; run it from a worktree** (owner, 25 Sep 2026). The tree is shared, so another session's uncommitted edits — a half-written test, a staged migration — are in every run you make from it, and for two days red runs were being called "machine load". Every commit is already made in a worktree (above), so the suite that matters — the one the pre-push hook runs before your push — never sees anybody else's edits. To test any other commit, do the same: `git worktree add --detach /tmp/epic-wt-<sha> <sha>`, copy `.env` in, symlink `node_modules` and `apps/api/node_modules`, `npm test` in `apps/api` (it still takes the shared lock), then `git worktree remove --force /tmp/epic-wt-<sha>`. A run from the shared tree is never evidence. What fails in the worktree is yours; what fails only in the shared tree is somebody's work in progress, and you name it rather than the machine. The other thing that was being called machine load — two sessions rebuilding the same test database under each other — is closed: `test/helpers/db.js` names each file's database with the process id as well, so a peer's run of the same file is a different database. The lesson is not the three fixes. Three separate causes were found for the one symptom in four days — the suite lock in a `$TMPDIR` no two sessions shared, the connection pool at ten per file, and the test databases named from the file alone — and each was found only because somebody refused to accept "machine load" as an answer. A red run has a cause; find it or name what you could not rule out. **The fourth cause, 25 Sep 2026, broke this very practice:** git exports `GIT_DIR` into hooks, and inside a linked worktree `git ls-files -- migrations` under it lists nothing (249 files without it, 0 with it), so the pre-push hook built every test database from an empty list and failed 358 tests with "relation does not exist" on a commit that had passed by hand in the same worktree a minute earlier. `.githooks/pre-push` now `unset`s `GIT_DIR GIT_WORK_TREE GIT_INDEX_FILE` first, and `test/helpers/db.js` refuses to build a database from an empty list while migrations sit on disk. If "relation does not exist" is everywhere, check for an exported `GIT_DIR` before anything else.
- Provider trials that expire on a clock (Yelp, TravelTime) are enabled only against a defined comparison, never "to see" — Technical Constraints §11.

## Architecture rules that are easy to break by accident

- The web bundle never holds a provider key. All third-party calls go through `apps/api` (Technical Constraints §13.7). `EXPO_PUBLIC_*` values are inlined at build time and are public by definition.
- Licensed place content is rented: store identifiers and household-generated annotations only. `trip_stops.venue_name` is a fixtures-only exception and must become fetch-at-display when a licensed source is enabled.
- **Rented and owned are two different layers, and code must not mix them.** A household act — shortlist, save, special, visited — claims a place, and `sources/own.js` then researches it from OpenStreetMap, the venue's own published page and the open encyclopedias, all of which we may keep for good. That research lands in `place_records` (Technical Constraints §13.10). A provider's name, hours, reviews, photos or rating never lands there, is never written to `household_places.venue` for a licensed ref, and never reaches a device. When a drawer needs a fact that survives the signal going, it comes from the owned record — not from a cached copy of somebody else's.
- **The data policy is V1 law** (`Supporting docs/Data policy/epic-data-policy.html`, 19 Sep 2026). Five sentences it all comes from: Google is the spine everywhere; nothing rented is stored; knowing what exists is free and permanent; ranking is done from what we own; we buy only for what is shown. In detail:
  - **Identifiers are the only provider content written down.** Google place ID, TripAdvisor location ID and the mapping between them are kept indefinitely; `lat`/`lng` for 30 days. Names, ratings, reviews, hours and photos live in memory for hours and never reach the database or a device. The Epic score is ours because it is *derived* — both providers' ratings and counts plus our own visits, household ratings, rank and recency, scaled 0–100 with a `scored_at` — never a stored copy of Google's 4.6.
  - **The census is free and permanent, and free means the IDs Only mask** (owner, 19 Sep 2026). Any search of an area not censused in 30 days slices Text Search on **`places.id` and nothing else** — one query per Google type inside each Epic subcategory, splitting any slice that returns its 60-place ceiling. Essentials is ids only: `places.location` and `places.types` are **Pro fields and bill**, so the census never asks for them. What the census alone writes to `place_index` is the id, the subcategory query that found it, the rank, the slice and the date seen. From then on an area's counts are known without calling Google, and a taxonomy change re-maps for free.
  - **Coordinates and Google types arrive with the first display search, not with the census.** They are written the first time a place is actually returned to a household, and coordinates expire at 30 days. Map placement and reachability therefore apply to *surfaced* places only — the area board never needs either, and must never be able to trigger anything dearer than IDs Only. Where the "Not on Google" by-name lookup matches an OpenStreetMap place, OSM's own coordinates may be kept for it (ODbL, attributed) as the reachability fallback.
  - **`skuFor` is strict, and stays strict.** Anything on Text Search beyond the IDs Only mask bills at Pro or above; the tier is read from the field mask because the mask is what Google prices. `test/census.test.js` pins each tier to its price so the census cannot drift back into the free column without somebody saying so out loud. Per-outcode request counts are a *rate* question now, not a cost one: keep the per-run ceiling for throughput and pace a ring under Google's QPS limit.
  - **Prefer search over detail, always.** One Text Search returns 20 places with ratings for one request; a Place Details call is one place. Never buy detail for a place a search could have covered. Rank the top 10 per category from `epic_score` (falling back to Google's rank), then buy one display search per category. Next page on scroll only. Photos only for tiles in the viewport, a row at a time.
  - **TripAdvisor is the drawer and nothing else** (owner, 19 Sep 2026, after experiment 3). It matched 33% of what a display search shows, held a quarter of Google's review depth, carried no family signal, and blending moved three of the top ten the wrong way. So: **no input to the Epic score** — that is Google plus Epic's own signals (visits, household ratings, rank, recency) — and **no lookup on the search path**. It is fetched live when a place is opened, matched on `latLong` at the shared 400 m fence and failing closed, and shown beside Google's with both logos per their display requirements. Storing the location id after a first open is gated on the owner confirming their terms; until then every open looks it up again. The verdict and its trigger are in `data_verdicts`.
  - **One paid research sweep is the exception to "no paid research pass per place in V1", and it is recorded here as one** (owner, 25 Sep 2026: "pay for it. £18–36 for 720 places, once, to build a vocabulary that then gets asked of hundreds of thousands for free"). The rule stands for enrichment sweeps; this is the one exception. What it is: twenty places a drawer (twelve top, eight mid-tail, `pickSample`) for every drawer with 100+ census places — 36 drawers, 720 places — researched by `sources/own.js` with `paid: true`, which buys at most two Place Details requests a place (identify it, then find its page; `google-pro`, 2.5p each) and nothing else paid. It runs as `sources/researchSweep.js`: priced before the click, refused without the request count its estimate reported, reserved through the collection ceiling a batch at a time, written place by place so a deploy loses nothing, and picked up at boot. It ran on 25 Sep 2026 as sweep `639a7090` over 37 drawers and 740 places (the census had grown), estimated at up to £27.32, and **cost £14.69** ($18.59): 581 Place Details requests on 413 places, 1.4 a place; 201 places were already held and free. It identified 454 places, matched 65 to the open map, read 196 venues' own pages and 62 encyclopedia entries, and left 316 with a description to read; 123 failed, 119 of them Overpass timeouts, none paid twice. Paying Google to *describe* places (the Google pass on the harvest) remains refused: "paying for Place Details to find a website is not the same as paying Google to describe places."
  - **Free data is a check on Google, not a second source of discovery or opinion.** OSM and the FSA hygiene register give the count the census is measured against, and the "Not on Google" residual, in the back office only. They are never *presented to a household* as a way of finding a place or of judging one, and there is no paid research pass per place in V1. **This does not touch the owned layer, which stays exactly as built** (owner, 19 Sep 2026): `place_records` remains what a device holds offline, menu links from venue pages remain in scope — menu -> order -> stars is a core epic — and owned facts may fill any field Google leaves empty on a place page.
  - **The drawer renders at once and never waits on a provider.** Draw it from the Epic score and Google immediately; the TripAdvisor panel fills in when its call returns and never blocks the first paint. With no signal the drawer shows the Epic score and owned facts only — both rented ratings simply are not there, and their absence must read as "not available offline" rather than as a place nobody has rated.
  - **A new source is earned, never assumed.** V2 opens only on a thin-page rate above ~15% on what households actually open, or a credible not-on-Google residual above 5% in a district.
  - Every paid control in the back office shows its price before the click, and the cost counter reads live from `provider_calls`. Purposes are stable strings: add, never rename.
- **Question sets and owned facts** (brief, 20 Sep 2026). A question set is a short, fixed list of closed questions asked of every place of a kind — a set is shared across subcategories, never owned by one — and **Google may raise a candidate word, but Google may never answer a question about a place.**
  - Review summaries (UK) and any other rented text are read in memory to extract candidate vocabulary only. Text is never written to disk, a log, or a debug field.
  - A `place_answer` is only stored when a source Epic owns or may freely read confirms it: the venue's own page, OSM, Wikipedia, Wikidata, FSA. Otherwise the answer is `asked_nothing_found` — a real answer, and a different fact from never having asked, which is the absence of a row.
  - Every stored answer carries source, source_url and checked_at. Two owned sources disagreeing is stored as unresolved, never silently resolved.
  - The harvest is a vocabulary run: nothing is stored against the places sampled, and candidate-to-place links are deleted once the candidate is promoted or ignored. Ignoring a word is permanent.
  - A question names an entry in `place_attributes` — our own label vocabulary — and never invents a second word list. The answer shape is the label's `kind`.
  - Enrichment is demand-driven. A place is answered when it crosses a usage threshold, never by a sweep; the hook is built and `EPIC_ENRICHMENT` is off.
  - The free-data sweep (OSM, venue pages, Wikipedia, Wikidata) may be scheduled and run in bulk. The Google pass may not, and refuses to start unless it is handed the request count its own estimate reported.
  - **Polarity is captured at extraction or not at all** (§5.1, 20 Sep 2026). "Does it have a wave machine? We couldn't find one" mentions the feature and means the opposite; once the rented text is discarded there is nothing to re-read. Every candidate carries asserted / denied / merely-asked counts.
  - **Only features become questions.** A condition (busy at weekends) and an opinion (rude staff) never do — opinions are the Epic score's job. A word nobody can call sits in the **holding pen**: not pending, not ignored, not waiting on a human, and reconsidered when a later harvest raises its count. Never force a verdict.
  - **Promotion needs no crawl.** Knowing wave machines are a real feature does not require visiting anybody's site; crawling is for answering a question about one place. Promotion is a human act on the reviewed list.
  - **Once a set's vocabulary is settled, Google leaves that category for good.** The Google pass skips it and enrichment reads owned sources only; attaching a new subcategory unsettles it. Expect the harvest's Google spend to trend to nothing.
  - **Enrichment triggers on the search, not on the open**, only for places actually returned to a household, never as a sweep — and the venue-page client asks `robots.txt` and keeps a per-domain crawl delay, centrally (`apps/api/src/sources/politeness.js`).
  - **No quote, no promotion (C21); the material, not the prompt (C22)** (owner, 26 Sep 2026). Promotable means *harvest-found and carrying an evidence quote from owned text*; a Google-raised word is never promoted on a classifier verdict alone. The rule sits in `quotedBy` / `PROMOTABLE_SQL` (`repositories/questionSets.js`) at every door — the write, the classifier's verdict, un-ignoring, and `promote()` itself — and migration 258 put the 8,770 context-free "features" back in the pen beside the 86 quoted ones. The sample that settled it: sixteen of twenty words the classifier had left unclear were fragments and review boilerplate; four would have settled with the drawer named. So re-classifying Google n-grams per drawer "is better prompting of the wrong material", and nothing further is spent on the pen; the global drain stays stopped. The second feature-harvest run waits for the prose change (venue-page paragraphs and Wikipedia bodies stored) — the handover's "no re-extract yet".
  - **No second Google pass on the harvest — decided, and the code refuses** (owner, 26 Sep 2026: "The 21 Sep run is conclusive — 41,816 words, nought promotable, and the commonest are staff, delicious, friendly. Record that verdict so nobody proposes it a third time"). The verdict is `data_verdicts.harvest.google-pass` (migration 251) and `googleHarvest` reads it before it quotes a price; reversing it is a new row that names it in `supersedes`, with evidence, never an edit. What replaced it is the drawer-level feature harvest (`sources/featureHarvest.js`): owned text, one call a drawer, sightings counted by us — its first complete run (26 Sep, 40 calls, £0.89) found swimming pool, sauna, steam room, waterfall, trig point, motte and bailey, roller coaster. Do not propose reading Google review summaries for vocabulary again.
- **If a value cannot be extracted from text, it cannot exist at Epic's scale** (owner, "The axes are dropped", 25 Sep 2026). The eight graded 0–4 axes — how thrilling, how much walking, how much planning, how new, how busy, how much you learn, how smart, how long a day — are cancelled and **graded judgement scores are not to be proposed again**. Each was a judgement no person could make twice the same way and no machine could read; everything that survives is a fact sitting in a sentence on a website. What a place carries is: categories with primary and secondary filing, yes/no labels, ranges (Suits ages, Duration), a cost band, and question sets per kind. A row is a rule over those and nothing else. The eight are deactivated, never deleted (migration 246): `scale` stays a kind the database accepts for the rows that exist, and nothing reads an inactive label.
- **A device may hold less than the server may.** Every API answer passes `apps/web/src/offline/policy.ts` before it is written to IndexedDB, and an endpoint not named there is not saved. Add new endpoints to that file deliberately; never make the fallback "save it unless it looks licensed".
- Every outbound provider call is attributed to a household and session in `provider_calls`; new integrations must log there before they are enabled.
- Allergens exclude; dislikes rank. They never share a control, a colour, or a code path.
- **The brand is the Epic pack v1** (`Supporting docs/Rebrand - EPIC`, September 2026), and it retires the Roam guidelines entirely (owner, 7 Sep 2026). Lime `#C8F542` is the brand and is used big and flat — the header, the primary action, and the moment something is selected. Ink `#201E1D` is every letter and every rule; cream `#FFFDF9` is the reading ground. Lime tint and moss are UI only. Square corners throughout, 2px ink rules, no shadows. **Never cream or white type on lime** (1.25:1); lime type only ever sits on ink. Archivo is the whole type system — there is no second face, and Caveat is gone. Every colour comes from `apps/web/src/theme.ts`; never a hex in a screen.
- **Roam red is retired, with one exception the owner kept**: allergen and overrun warnings stay red, because they mean danger rather than brand (7 Sep 2026). The loved heart is ink now. Nothing else in the app is red.
- **The mark is drawn, not a file.** `apps/web/src/components/Wordmark.tsx` — "Epic" in Archivo 800 at −0.06em with the pin as the dot of a dotless ı. The pin never sits beside the word, is never recoloured, and below 24px the wordmark becomes the pin alone. `docs/brand/README.txt` is the reference; the strapline is "Seize the day".
- Voice is interpreted against a closed set that is visible on screen, and every voice action has a tap equivalent that produces the same state change.
- While the household is speaking, the screen shows only the live transcript (`Listening` component): suggestions and everything else collapse, listening continues until they tap Done, and nothing is sent before then. Use `useSpeech` (continuous, accumulating) for every mic; never send on the first pause. Exception (owner, 3 Sep 2026, Plan screen): the criteria rows stay in view and fill as the words arrive (`/api/plan/preview`), with a small live box and one red Stop; the rest of the rule holds. That Stop is the third thing allowed to be red, beside allergens and overruns — it is an urgent action, not brand colour.
- Options are composed from one retrieved pool; adding an option must not add a provider call.
- **Five tabs: Inspire · Places · Trips · Host · Settings** (owner, 12 Sep 2026, Groups & events NEW). Household is folded into Settings ("You and yours"); the Host tab is hosting only — nothing to browse there. A host's **kind** (I have a skill / Meetups and mini tours / Expert guide) is never a rank, a sort or a price band; an offer's **shape**, **visibility** and **money** are three independent axes and the set-up's steps come from them (`stepsFor`); **trust** (Verified / Checked / Epic Trusted) is set in the back office and never by the host. Public experiences are Epic-collects only, and until a payment provider exists a booking is *recorded*, never described as paid. Technical Constraints §13.18.
- **Every page has an address, and the address is what decides what is drawn** (owner, 5 Sep 2026: "Every page of our site needs a unique URL… 2 layers in, I should be able to share a URL with someone, and they should be able to get to the exact point that I was on"). `src/routes.ts` is the only place a URL is spelled; `src/router.tsx` is the only thing that reads or writes the address bar. A new screen or a new layer inside one is not done until it has a route in `routes.ts` and a case in `test/routes.test.ts`. The path is the page (`/trips/<id>/day/<dayId>`); the query is how that page is set (`?kind=eat`, `?place=<ref>`), and only what differs from the default is written down. A move pushes, a filter replaces. Never read or write `window.location` or `window.history` from a screen. Technical Constraints §13.14.

## Web and mobile are one layout system (owner, 3 Sep 2026)

The owner reviews every screen in both views on the deployed site: the shell (`apps/web/App.tsx`) carries a Web / Mobile toggle on any window 900px or wider, and "Mobile" draws the whole app inside a 390px phone frame. New screens and components must follow the structure that makes that work:

- **Never read the window directly.** Use `useViewport()` from `apps/web/src/hooks/useViewport.tsx` for width and height, not `useWindowDimensions`, `Dimensions` or `window.innerWidth`. The frame tells screens they are 390px wide through that hook; anything reading the window ignores the toggle and shows the desktop layout inside the phone.
- **Every screen has a phone layout and a wide layout**, decided from that width (breakpoints in use: 680 for the date picker, 900 for the shell, household and drawer, 1000 for Places and Trips). Design both before calling a screen done, and check both with the toggle on the Railway deployment, not only on a desktop window.
- **Anything that portals out of the tree (a `Modal`) must pin itself to the frame.** Read `framed` and `origin` from `useViewport()` and position the sheet at that origin with the frame's size, as `VenueDrawer` does; otherwise it covers the whole browser window.
- **Keep one tree shape across layouts.** A screen that returns two different trees for wide and narrow loses its state when the owner flips the toggle. Branch on style and on which children render, not on the whole return.
- **Icons come from one set.** `apps/web/src/components/Icon.tsx` wraps Lucide (`lucide-react-native`); use `<Icon name=…>`, `<CategoryIcon>`, `<IconText>` and `<Rating>`, or the `icon` prop on `Chip` and `Button`. Never an emoji or a symbol character (★ ♥ ✕ ✓ 🎙 📍 …) as an icon; the owner called that embarrassing (3 Sep 2026). Add a name to the set rather than importing a glyph in a screen.
- **Content must fit 390px.** Rows wrap, chips shrink (`Chip` already wraps long labels), and nothing is allowed to overflow the frame horizontally.
